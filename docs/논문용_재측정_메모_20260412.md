# EdgePPE-Net 재측정 메모

작성일: 2026-04-12

이 문서는 기존 벤치마크 결과에 대해 추가로 수행한 재측정 및 원인 분석 결과를 정리한 메모이다. 주된 목적은 다음 세 가지였다.

1. USB Coral 속도 수치가 warmup이나 전처리 포함 때문에 왜곡된 것인지 확인
2. `worker AP`가 비정상적으로 낮게 나온 원인 확인
3. Table 3에서 recall을 더 높일 수 있는지 간단한 sweep으로 점검

## 1. USB Coral 속도 재측정

### 1-1. 기존 측정 방식 확인

현재 `test_ppe_rpi5.py`의 `run_inference()`는 다음 순서로 동작한다.

- 입력 전처리: `prepare_detector_input(...)`
- **타이머 시작**
- `interp.invoke()`
- **타이머 종료**

즉, 기존 `infer_ms`는 **순수 inference 구간만** 측정하며, 이미지 로딩과 전처리는 포함하지 않는다.

### 1-2. detection test set에서 warmup 제외 평균

34장 detection test set의 per-image inference time에서 첫 1~2장을 제외한 평균은 다음과 같다.

| Runtime | 전체 평균 | 첫 1장 제외 | 첫 2장 제외 |
|---|---:|---:|---:|
| CPU | 26.3833 ms | 26.3139 ms | 26.2873 ms |
| Coral USB | 62.6207 ms | 58.5010 ms | 58.3787 ms |
| PCIe HAT | 21.4544 ms | 20.8115 ms | 20.7915 ms |

해석:

- USB Coral은 첫 프레임 warmup 영향이 매우 컸다.
- 그러나 warmup을 제외해도 USB Coral은 약 **58.38 ms/image**로 여전히 CPU보다 느렸다.

### 1-3. 단일 이미지 반복 벤치 (warmup 5회, repeats 30회)

같은 이미지 1장을 반복 추론한 결과는 다음과 같다.

| Runtime | Mean | Median | Min | Max |
|---|---:|---:|---:|---:|
| CPU | 26.53 ms | 26.54 ms | 26.38 ms | 26.74 ms |
| Coral USB | 56.85 ms | 55.33 ms | 55.16 ms | 60.82 ms |
| PCIe HAT | 21.18 ms | 21.18 ms | 21.14 ms | 21.25 ms |

결론:

- USB Coral이 느린 것은 warmup 때문만은 아니다.
- 전처리 포함 여부와 무관하게, 본 Pi 5 환경에서는 **USB Coral의 순수 inference latency 자체가 CPU보다 느리게 측정되었다.**
- 따라서 논문에는 기존 15.50 ms 수치를 그대로 유지하기보다, 본 실험 환경에서는 USB Coral이 기대보다 비효율적이었다는 점을 솔직하게 적는 편이 안전하다.

논문용 문장 예시:

> 추가 재측정 결과, USB Coral의 초기 warmup 영향을 제외하더라도 평균 추론 시간은 약 58.38 ms/image로 나타났다. 또한 단일 이미지 반복 추론에서도 56.85 ms의 평균 지연이 측정되어, 본 Raspberry Pi 5 환경에서는 USB Coral의 순수 추론 지연이 CPU 및 PCIe HAT 구성보다 불리함을 확인하였다.

## 2. worker AP가 낮은 원인

### 2-1. GT 클래스 분포 확인

`coco_test/_annotations.coco.json`의 관련 클래스 수는 다음과 같다.

| GT class | Count |
|---|---:|
| person | 4 |
| no-hardhat | 7 |
| no-safety vest | 3 |
| no-mask | 2 |
| hardhat | 32 |
| safety vest | 2 |

문제는 기존 detection metric 계산에서 `worker`에 대응되는 GT가 사실상 `person` 4개만 반영되고, `no-hardhat / no-safety vest / no-mask`는 worker로 간주되지 않았다는 점이다.

즉, 기존 `worker GT total = 4`는 실제 작업자 수를 과소반영한 값이다.

### 2-2. worker-like GT로 재해석한 경우

다음 클래스들을 모두 worker로 간주하여 다시 점검하였다.

- `person`
- `no-hardhat`
- `no-safety vest`
- `no-mask`

이 경우 worker GT 수는 총 16개가 된다.

CPU detection 결과에서 worker AP@0.5는 다음과 같이 나타났다.

| Worker GT 해석 | worker GT total | worker AP@0.5 |
|---|---:|---:|
| 기존 계산 (`person`만) | 4 | 0.1662 |
| worker-like 재해석 | 16 | 0.0547 |

또한 worker threshold를 낮추는 sweep도 수행했으나, `0.25`로 낮춘다고 해서 AP가 유의미하게 개선되지는 않았다.

| worker threshold | Matched GT | Missed GT | worker AP@0.5 |
|---|---:|---:|---:|
| 0.38 | 4 | 12 | 0.0468 |
| 0.25 | 4 | 12 | 0.0468 |
| 0.05 | 6 | 10 | 0.0508 |

### 2-3. 실제 원인

각 worker-like GT에 대해 가장 잘 맞는 person prediction의 IoU를 확인해보면, 상당수가 0.5 미만이었다.

예시:

- `no-mask` GT 중 일부: IoU 0.03, 0.13
- `no-hardhat` GT 중 일부: IoU 0.08, 0.10, 0.15, 0.17
- `no-safety vest` GT 중 일부: IoU 0.23

반면 일부 `person` GT는 IoU 0.69~0.97로 잘 맞았다.

결론:

- `worker AP` 저하는 단순 threshold 문제라기보다,
  - GT 라벨 구조가 worker/person detection 평가에 불리하고
  - missing-PPE 인물에 대해 예측 bbox가 GT bbox와 충분히 겹치지 못한
    **도메인/box alignment 문제**에 가깝다.

논문용 문장 예시:

> 추가 분석 결과, detection test set에서는 `no-hardhat`, `no-safety vest`, `no-mask`와 같이 실제로는 작업자에 해당하는 인스턴스가 별도 클래스명으로 주석되어 있어, worker AP가 불안정하게 측정되었다. 이들을 worker-like ground truth로 재해석한 경우에도 IoU 0.5 기준에서 person bbox 정합성이 낮게 나타나, worker AP는 threshold 조정보다 annotation 구조와 bbox alignment의 영향을 크게 받는 것으로 확인되었다.

## 3. Table 3 recall 회복 시도

현재 보수적 설정에서의 Table 3 결과는 다음과 같다.

| Method | Precision | Recall | F1 | FP Rate |
|---|---:|---:|---:|---:|
| Box IoU only | 0.8500 | 0.8095 | 0.8293 | 0.0811 |
| EdgePPE-Net (current conservative) | 1.0000 | 0.6667 | 0.8000 | 0.0000 |

### 3-1. 사람 형체 필터 완화 sweep

다음과 같은 완화 설정들을 시험하였다.

- relax1:
  - `CONF_THRESHOLDS.person = 0.30`
  - `PERSON_SHAPE_STRONG_POSE_SCORE_THRESHOLD = 0.35`
  - `PERSON_SHAPE_MIN_VISIBLE_KEYPOINTS = 4`
  - `PERSON_SHAPE_POSE_MIN_SCORE = 0.35`
  - `PERSON_SHAPE_NO_POSE_MIN_SCORE = 0.45`
- relax2:
  - `CONF_THRESHOLDS.person = 0.32`
  - `PERSON_SHAPE_STRONG_POSE_SCORE_THRESHOLD = 0.38`
  - `PERSON_SHAPE_MIN_VISIBLE_KEYPOINTS = 5`
  - `PERSON_SHAPE_POSE_MIN_SCORE = 0.40`
  - `PERSON_SHAPE_NO_POSE_MIN_SCORE = 0.50`
- permissive:
  - 사람 형체 필터를 거의 해제한 수준의 완화 설정

결과:

| Setting | Precision | Recall | F1 | FP Rate |
|---|---:|---:|---:|---:|
| current conservative | 1.0000 | 0.6667 | 0.8000 | 0.0000 |
| relax1 | 0.9333 | 0.6667 | 0.7778 | 0.0270 |
| relax2 | 1.0000 | 0.6667 | 0.8000 | 0.0000 |
| permissive | 0.9333 | 0.6667 | 0.7778 | 0.0270 |

해석:

- 사람 형체 필터를 완화해도 recall은 거의 회복되지 않았다.
- 오히려 일부 설정에서는 FP가 다시 증가하여 F1이 더 나빠졌다.

### 3-2. PPE match threshold 조정

- `HELMET_MATCH_SCORE_MIN`
- `VEST_MATCH_SCORE_MIN`

을 각각 `0.08`, `0.10`으로 높여보았으나 결과는 baseline과 동일하였다.

즉, 현재 recall 저하는 PPE 매칭 임계값보다 **상위 단계의 detection/association 문제** 영향이 더 큰 것으로 보인다.

### 3-3. CPU detector model 기준 current code 결과

알고리즘 비교를 하드웨어와 분리해서 보기 위해, current code를 CPU detector model 기준으로도 재측정하였다.

| Method | Precision | Recall | F1 | FP Rate |
|---|---:|---:|---:|---:|
| Box IoU only (CPU detector) | 0.9000 | 0.8571 | 0.8780 | 0.0541 |
| EdgePPE-Net (CPU detector) | 0.8889 | 0.7619 | 0.8205 | 0.0541 |

해석:

- current code 기준에서도 EdgePPE-Net이 box-only baseline보다 높은 recall/F1을 만들지는 못했다.
- 즉, **현재 20-frame subset에서는 EdgePPE-Net의 강점이 recall 향상보다는 conservative false-positive suppression 쪽에 더 가깝게 나타난다.**

## 4. 최종 권고

### 권고 1: USB Coral 속도 서술

논문에는 다음처럼 쓰는 것이 가장 안전하다.

- USB Coral은 참고용 비교로 유지
- 단, 본 Pi 5 환경 실측에서는 PCIe HAT보다 현저히 느렸음을 명시
- 가능하면 "초기 예상과 달리" 또는 "실험 환경 의존적"이라는 문장으로 방어

### 권고 2: worker AP 서술

worker AP는 높은 수치를 만들기 어렵다. 따라서 다음과 같이 방어하는 것이 적절하다.

- detection benchmark의 worker score는 GT annotation 구조 영향이 큼
- 반면 helmet AP는 상대적으로 안정적
- PPE 판정 실험의 핵심은 worker detector 단독 성능이 아니라 worker-PPE association과 오탐 감소에 있음

### 권고 3: Table 3 서술

현재 subset만 놓고 보면, 가장 방어하기 좋은 방향은 다음 중 하나이다.

1. **보수적 설정 유지**
   - Precision 1.0
   - FP Rate 0.0
   - Recall 감소는 conservative setting으로 해석
2. **추가 GT 수집 후 재실험**
   - hand-held PPE
   - both-missing

현재 sweep 결과만으로는 recall을 크게 끌어올리면서 FP를 유지하는 설정을 찾지 못했다.

논문용 문장 예시:

> 제안한 EdgePPE-Net은 현재 실험 subset에서 FP Rate를 0으로 낮추는 보수적 동작점을 형성하였다. 추가적인 임계값 완화 실험을 수행하였으나 recall의 유의미한 회복은 관찰되지 않았으며, 일부 경우 오히려 false positive가 증가하였다. 따라서 본 시스템은 현재 설정에서 오탐 억제를 우선하는 안전 모니터링 모드로 해석할 수 있다.

## 5. 결론적으로

재측정 결과, 다음은 비교적 확실하게 말할 수 있다.

1. USB Coral이 느린 것은 warmup 때문만은 아니다.
2. worker AP 저하는 단순 threshold보다 GT 구조와 bbox alignment 문제 영향이 크다.
3. 현재 subset에서는 EdgePPE-Net의 장점이 recall 향상보다 오탐 억제에 더 강하게 나타난다.
4. 논문 방어력을 가장 크게 올려줄 추가 작업은 여전히 다음 두 가지다.
   - hand-held PPE 장면 추가
   - both-missing 장면 추가
